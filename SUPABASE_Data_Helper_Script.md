# Supabase Data Helper Script

How to connect to the Frontier Forms Supabase project, what data is already loaded, and how to query or reload it.

> **Everything in the database is synthetic** (generated by [Synthea](https://github.com/synthetichealth/synthea)). No real patient data. Names, SSNs (`999-xx-xxxx`), phones (`555-…`) and addresses are fake.

---

## 2. Setup

### 2.1 `.env`

Put the shared `.env` file (sent on Discord) in the repo root. It is git-ignored. It must contain:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=...            # https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=... # browser-safe key; RLS blocks it from every table right now
DATABASE_URL=...                         # Postgres, SESSION POOLER string (see note below)
SUPABASE_PASSWORD=...
```

**Use the session pooler for `DATABASE_URL`** (`aws-0-us-east-2.pooler.supabase.com:5432`, user `postgres.<project-ref>`). The direct host `db.<ref>.supabase.co` is IPv6-only and fails on most home/office networks with `ENOTFOUND`.

Never commit `.env`, and never put `DATABASE_URL` or the password in client-side (Next.js `NEXT_PUBLIC_*`) code.

### 2.2 Python environment

```bash
python3 -m venv .venv
.venv/bin/pip install -r scripts/requirements.txt
```

### 2.3 Connection check

```bash
.venv/bin/python - <<'EOF'
import os, psycopg
from dotenv import load_dotenv
load_dotenv(".env")
with psycopg.connect(os.environ["DATABASE_URL"], sslmode="require") as c:

EOF
```

Expected output: `(100,)`

## 3. Data model (what was loaded)

### `patient_passports` — one row per patient

| Column | Contents |
|---|---|
| `synthetic_id` | `SYN-00001` … `SYN-00100` |
| `display_name` | e.g. `Abraham Hackett` (Synthea's numeric name suffixes like `Hackett68` are stripped) |
| `demographics` | `given_name`, `middle_names`, `family_name`, `maiden_name`, `prefix`, `date_of_birth`, `gender`, `birth_sex`, `race`, `ethnicity`, `marital_status`, `preferred_language`, `birth_place`, `synthetic_ssn`, `synthea_patient_id`, `dataset` |
| `contact` | `phone`, `address { line[], city, state, postal_code, country }` |
| `insurance` | `payer`, `uninsured`, `as_of`, `source` — from the most recent ExplanationOfBenefit (Synthea has no Coverage resources) |
| `owner_id` | `NULL` for now (no auth users yet) |

### `passport_facts` — fact keys

| `fact_key` | Rows | Patients | `value` shape |
|---|---|---|---|
| `allergy.environment` / `allergy.food` / `allergy.medication` | 71 / 21 / 7 | 18 / 15 / 7 | `substance, type, criticality, clinical_status, reactions[]` |
| `condition.active` | 795 | 93 | `name, code, semantic_tag, clinical_status, onset, abatement` |
| `condition.resolved` | 2,256 | 99 | same as above |
| `medication.active` | 219 | 59 | `name, code, request_status, dose_quantity, frequency, period, period_unit, as_needed, reason[], authored_on` |
| `medication.past` | 2,797 | 95 | same as above |
| `immunization.history` | 1,390 | 100 | `vaccine, code, date, status` |
| `vitals.height` / `vitals.weight` / `vitals.bmi` / `vitals.heart_rate` | ~100 each | | `value, unit, observed_at` (latest observation only) |
| `vitals.blood_pressure` | 100 | 100 | `systolic, diastolic, unit, observed_at` |
| `social.smoking_status` | 100 | 100 | `value, code, observed_at` |
| `insurance.primary` | 100 | 100 | `payer, uninsured, as_of` |

- `code` values use FHIR token form `system|code`, e.g. `http://www.nlm.nih.gov/research/umls/rxnorm|314076`.
- `status`: active allergies/conditions/meds are `known`. "Active vs past" is encoded in the `fact_key`, not in `status`. No `missing` facts are generated yet; per Spec §4.4 the gold-label code should decide what counts as missing.
- `semantic_tag` is the SNOMED suffix (`disorder`, `finding`, `situation`, …). **Filter on it.** Conditions include non-clinical items such as `Medication review due (situation)` and `Full-time employment (finding)`.
- Patients span all ages, including newborns. Synthea vitals for infants can look odd (e.g. adult-range BP).

### `source_records`

One row per FHIR resource behind a fact: `fhir_resource_type`, `fhir_resource_id`, `clinical_code`, `effective_at`, `source_file_path` (the bundle filename inside the Synthea zip), and `payload` (full FHIR JSON, minus the narrative `text`).

## 4. Useful queries

Run these in the Supabase SQL editor or through `psycopg`.

```sql
-- Patient list
select synthetic_id, display_name, demographics->>'date_of_birth' as dob,
       demographics->>'gender' as gender, insurance->>'payer' as payer
from patient_passports order by synthetic_id;

-- Everything known about one patient
select f.fact_key, f.status, f.value
from passport_facts f join patient_passports p on p.id = f.passport_id
where p.synthetic_id = 'SYN-00001'
order by f.fact_key, f.valid_from desc;

-- Active medications (what an intake form would ask for)
select p.synthetic_id, f.value->>'name' as medication, f.value->>'authored_on' as since
from passport_facts f join patient_passports p on p.id = f.passport_id
where f.fact_key = 'medication.active'
order by 1, 2;

-- Active clinical diagnoses only (drop findings/situations)
select p.synthetic_id, f.value->>'name' as condition
from passport_facts f join patient_passports p on p.id = f.passport_id
where f.fact_key = 'condition.active' and f.value->>'semantic_tag' = 'disorder';

-- All allergies
select p.synthetic_id, f.fact_key, f.value->>'substance' as substance, f.value->>'criticality' as criticality
from passport_facts f join patient_passports p on p.id = f.passport_id
where f.fact_key like 'allergy.%';

-- Provenance: the raw FHIR resource behind a fact
select s.fhir_resource_type, s.fhir_resource_id, s.payload
from passport_facts f join source_records s on s.id = f.source_record_id
where f.id = '<fact uuid>';

-- Patients with good intake-form coverage (has allergies AND active meds)
select p.synthetic_id, p.display_name
from patient_passports p
where exists (select 1 from passport_facts f where f.passport_id = p.id and f.fact_key like 'allergy.%')
  and exists (select 1 from passport_facts f where f.passport_id = p.id and f.fact_key = 'medication.active');
```

Python example:

```python
import os, psycopg
from dotenv import load_dotenv
from psycopg.rows import dict_row

load_dotenv(".env")
with psycopg.connect(os.environ["DATABASE_URL"], sslmode="require", row_factory=dict_row) as conn:
    facts = conn.execute(
        """select f.fact_key, f.value from passport_facts f
           join patient_passports p on p.id = f.passport_id
           where p.synthetic_id = %s and f.fact_key = any(%s)""",
        ("SYN-00001", ["medication.active", "allergy.medication", "allergy.food"]),
    ).fetchall()
```

## 5. Re-importing / loading more patients (only if needed)

The data is already loaded, so **skip this section unless you want to reload or add patients.**

```bash
# 1. Download the Synthea sample into a temp folder (24 MB zip, ~313 MB unzipped)
mkdir -p /tmp/synthea && cd /tmp/synthea
curl -L -o fhir.zip https://synthetichealth.github.io/synthea-sample-data/downloads/latest/synthea_sample_data_fhir_latest.zip
unzip -q fhir.zip -d bundles
cd -

# 2. Import (living patients only, sorted by Synthea patient UUID)
.venv/bin/python scripts/import_fhir.py /tmp/synthea/bundles --limit 100
```

- The import is **idempotent per `synthetic_id`**: each patient's passport row is upserted, and its facts and source records are deleted and re-inserted. Each patient runs in its own transaction.
- `synthetic_id`s are assigned in order (`SYN-00001` = first selected bundle). Re-running with the same zip and `--limit` gives the same mapping. A *different* zip or limit reassigns IDs, so don't do that once forms/evaluations reference passports.
- `--include-deceased` also imports deceased patients.
- The sample only has 112 patients (100 living). For more, generate with Synthea (requires Java 17+): `java -jar synthea-with-dependencies.jar -p 1000 --exporter.fhir.export true`.

### Applying the schema to a *fresh* Supabase project

Not needed for our shared project, where the schema is already applied. For a new project:

```bash
.venv/bin/python - <<'EOF'
import os, psycopg
from dotenv import load_dotenv
load_dotenv(".env")
sql = open("supabase/migrations/20261102000000_initial_schema.sql").read()
with psycopg.connect(os.environ["DATABASE_URL"], sslmode="require") as c:
    c.execute(sql)
EOF
```

The migration was applied with this snippet, not the Supabase CLI, so `supabase db push` won't know about it. If the team adopts the CLI later, mark it applied with `supabase migration repair --status applied 20261102000000`.

## 6. Security notes

- RLS is **on** for every table, and the only policy is "owners read their own passport". The publishable/anon key therefore **cannot read any data** right now. Server code must use `DATABASE_URL` (or a future service-role key) and stay server-side.
- Add explicit RLS policies before exposing anything through the browser Supabase client.
- The DB password was shared over Discord. Spec §8 says not to, so **rotate it** (Dashboard → Project Settings → Database) before anything beyond the hackathon, and update `.env`.
